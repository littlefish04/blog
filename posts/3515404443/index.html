    一、加载和存储的性能

    所有现代处理器都包含一个或多个高速缓存（cache）存储器，以便对这种容量很小的存储器提供快速的访问。本节进一步研究涉及加载（从内存读到寄存器）和存储（从寄存器写到内存）操作的程序的性能，并且只考虑所有的数据都存放在高速缓存中的情况。

    1.1 加载的性能

    加载单元流水线

    现代处理器有专门的功能单元来执行加载和存储操作，这些单元有内部的缓冲区，用来保存未完成的内存操作请求的集合。例如，我们的参考机有两个加载单元，每一个可以保存多达 72 个未完成的读请求；它还有一个存储单元，其存储缓冲区最多能保存 42 个写请求。每个这样的单元通常都可以每个时钟周期开始一个操作。

    一个包含加载操作的程序的性能，既依赖于加载单元流水线的能力，也依赖于加载单元的延迟。在参考机上运行合并操作的实验中，我们看到：除了使用 SIMD 操作时以外，对任何数据类型组合和合并操作来说，CPE 从未低于 0.50。制约这些示例 CPE 的一个因素是，对每个被计算的元素，所有示例都需要从内存中读一个值，而两个加载单元每个时钟周期只能启动两条加载操作，所以 CPE 不可能小于 0.50。也就是说，对于每个被计算的元素必须加载 个值的应用，CPE 不可能低于 。

    加载操作的地址只依赖于循环索引 i，所以加载操作不会成为限制性能的关键路径的一部分。因此到目前为止，我们在示例中还没有看到加载操作的延迟产生的影响。

    加载操作延迟的影响

    要确定一台机器上加载操作的延迟，我们可以建立由一系列加载操作组成的一个计算，其中一条加载操作的结果决定下一条操作的地址。作为一个例子，考虑图 5-31 中的函数 list_len，它计算一个链表的长度。在这个函数的循环中，变量 ls 的每个后续值都依赖于指针引用 ls->next 读出的值。测试表明，函数 list_len 的 CPE 为 4.00，我们认为这直接表明了加载操作的延迟。

    1.2 存储的性能

    在迄今为止所有的示例中，我们只分析了大部分内存引用都是加载操作的函数，也就是从内存位置读到寄存器中。与之对应的是存储（store）操作，它将一个寄存器值写到内存。这个操作的性能，尤其是它与加载操作的相互关系，涉及一些很细微的问题。

    存储单元流水线

    与加载操作一样，在大多数情况中，存储操作都能够在完全流水线化的模式中工作，每个周期开始一条新的存储。例如，考虑图 5-32 中所示的函数，它将一个长度为 的数组 dest 的元素设置为 0。我们测试的结果为 CPE 等于 1.00，对于只具有单个存储功能单元的机器来说，这已经达到了最佳情况。

    图 5-32 将一个长度为 的数组 dest 的元素全部设置为 0。

    1.3 加载和存储操作的互相影响

    与到目前为止我们已经考虑过的其他操作不同，存储操作并不影响任何寄存器值。因此，就其本性来说，一系列存储操作不会产生数据相关。只有加载操作会受存储操作结果的影响，因为只有加载操作能从由存储操作写入的那个位置读回值。

    write_read 函数

    图 5-33 所示的函数 write_read 说明了加载和存储操作之间可能的相互影响。这幅图也展示了该函数的两个示例执行，它们都是在两元素数组 a 上调用的，该数组的初始内容为 -10 和 17，参数 cnt 等于 3。这些执行说明了加载和存储操作的一些细微之处。

    图 5-33a 写和读内存位置的代码。

    写/读相关

    在图 5-33 的示例 A 中，参数 src 是一个指向数组元素 a[0] 的指针，而 dest 是一个指向数组元素 a[1] 的指针。在此种情况中，指针引用 *src 的每次加载都会得到值 -10。因此，在两次迭代之后，两个数组元素就会分别固定为 -10 和 -9。从 src 读出的结果不受对 dest 的写的影响。在较大次数的迭代上测试这个示例，得到 CPE 等于 1.3。

    在图 5-33 的示例 B 中，参数 src 和 dest 都是指向数组元素 a[0] 的指针。在这种情况中，指针引用 *src 的每次加载都会得到指针引用 *dest 的前一次执行存储的值。因而，一系列不断增加的值会被存储在这个位置。通常，如果调用函数 write_read 时参数 src 和 dest 指向同一个内存位置，而参数 cnt 的值为 （ ），那么净效果是将这个位置设置为 。这个示例说明了一个现象，我们称之为写/读相关（write/read dependency）——一个内存读的结果依赖于一个最近的内存写。我们的性能测试表明，示例 B 的 CPE 为 7.3，写/读相关导致处理速度下降约 6 个时钟周期。

    加载和存储单元的细节

    为了了解处理器如何区别这两种情况，以及为什么一种情况比另一种运行得慢，我们必须更加仔细地看看加载和存储执行单元，如图 5-34 所示。存储单元包含一个存储缓冲区，它保存已经被发射到存储单元而又还没有完成的存储操作的地址和数据，这里的完成包括更新数据高速缓存。提供这样一个缓冲区，使得一系列存储操作不必等待每个操作都更新高速缓存就能够执行。当一个加载操作发生时，它必须检查存储缓冲区中的条目，看有没有地址相匹配。如果有地址相匹配（意味着在写的字节与在读的字节有相同的地址），它就取出相应的数据条目作为加载操作的结果。

    二、确认和消除性能瓶颈

    至此，我们只考虑了优化小的程序。在这样的小程序中，有一些很明显限制性能的地方，因此我们很容易把注意力集中在它们身上。而在处理大程序时，连知道应该优化什么地方都是很难的。本节会描述如何使用代码剖析程序（code profiler）——这是一种在程序执行时收集性能数据的分析工具。

    2.1 程序剖析

    程序剖析（profiling）会运行程序的一个特殊版本，其中插入了工具代码，以确定程序的各个部分各需要多少时间。这对于确认程序中我们需要集中注意力优化的部分很有用。剖析的一个有力之处在于，它可以在现实的基准数据（benchmark data）上运行实际程序的同时进行剖析。

    Unix 系统提供了一个剖析程序 GPROF。这个程序产生两种形式的信息：首先，它确定程序中每个函数花费了多少 CPU 时间；其次，它计算每个函数被调用的次数，并按调用它的函数来分类。这两种信息都非常有用——计时信息给出了不同函数在决定整体运行时间时的相对重要性，调用信息则使我们能够理解程序的动态行为。

    GPROF 有些属性值得注意：

    • 计时不是很准确。它的计时基于一个简单的间隔计数（interval counting）机制，编译过的程序为每个函数维护一个计数器，记录花费在执行该函数上的时间。操作系统会以某个规则的时间间隔 中断程序一次， 的典型值范围为 1.0～10.0 毫秒。当中断发生时，它会确定程序正在执行什么函数，并将该函数的计数器值增加 。当然，也可能这个函数只是刚开始执行，而很快就会完成，却赋给它从上次中断以来整个的执行花费。在两次中断之间也可能运行了其他某个程序，却因此根本没有计算那个程序的花费。

      对于运行时间较长的程序，这种机制工作得相当好。不过，对于那些运行时间少于 1 秒的程序来说，得到的统计数字只能看成是粗略的估计值。

    • 假设没有执行内联替换，则调用信息相当可靠。编译过的程序为每对调用者和被调用者维护一个计数器，每次调用一个过程时，就会对适当的计数器加 1。

    • 默认情况下，不会显示对库函数的计时。相反，库函数的时间都被计算到调用它们的函数的时间中。
